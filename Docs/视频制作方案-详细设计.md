## 1. 共用基础设施与集成规范

五个方案共享的输入源、数据结构、服务形态、合成约定统一在此定义，各方案章节只描述差异部分。

### 1.1 与现有系统的数据流衔接

现有链路终点：`hotspot-monitor-service`（8000 端口）的 `topics` 表（LLM 提取、pgvector 去重）与 `creator_videos.transcript`（SenseVoice 转写）。视频制作链路从这两张表取数〔历史:现行 studio 选题由 LLM 自主命题+查重缓存,不接热点库〕：

```
topics / creator_videos.transcript          ←—— 现有数据（输入）
        │
        ▼
video_script（新增表：口播稿，含分句结构）     ←—— 文案环节（各方案实现不同）
        │
        ▼
video_project（新增表：制作任务主表）
        │
        ├── tts_audio（配音资产，方案二/三/四）
        ├── visual_assets（画面素材/分镜，各方案不同）
        └── subtitle_tracks（字幕轨）
        │
        ▼
ffmpeg 合成管线（各方案共用同一合成器）
        │
        ▼
finished_videos（新增表：成片元数据 + 文件路径）
```

**取数接口**：不直连 ORM，走 hotspot 现有 service 层模式新增一个只读查询（或直接 SQL 读 `topics` 表），避免复用 `api/routes.py`（现状该文件缺 `typing` 导入，列表端点运行时 NameError，见系统现状文档问题清单 #1）。

### 1.2 新增数据表设计

统一表结构（方案二/三/四完整使用；方案一只用 `video_project` + `finished_videos`；方案五只做任务记录）：

```sql
-- 制作任务主表
CREATE TABLE video_project (
    id            BIGSERIAL PRIMARY KEY,
    topic_id      BIGINT REFERENCES topics(id),          -- 源选题
    video_id      BIGINT REFERENCES creator_videos(id),  -- 源视频（可空）
    scheme        VARCHAR(16) NOT NULL,   -- 'nb_pure' | 'nb_video' | 'cosy' | 'mpt' | 'jianying'
    status        VARCHAR(16) NOT NULL DEFAULT 'pending',
        -- pending / scripting / voicing / rendering / done / failed
    script        JSONB,                  -- 见 1.3 分句结构
    params        JSONB,                  -- 方案特定参数（voice_id、模板 id、分辨率等）
    error         TEXT,
    created_at    TIMESTAMPTZ DEFAULT now(),
    updated_at    TIMESTAMPTZ DEFAULT now()
);

-- 口播稿（方案一为 ASR 反写结果，方案二/三/四为 LLM 直写，方案五为投喂剪映前的文本）
-- 实际上 script 直接以 JSONB 存在 video_project.script 中，不单独建表。

-- 音色资产（方案二/三/四）
CREATE TABLE tts_voice (
    id            BIGSERIAL PRIMARY KEY,
    voice_id      VARCHAR(64) UNIQUE NOT NULL,   -- 引擎内注册 id（如 cosyvoice 的 {uuid}）
    name          VARCHAR(64) NOT NULL,
    engine        VARCHAR(32) NOT NULL,          -- 'cosyvoice2-local' | 'siliconflow' | ...
    sample_path   TEXT NOT NULL,                 -- 3~10s 录音样本落盘路径
    meta          JSONB,                         -- 采样率、时长、录音质量自检结果
    created_at    TIMESTAMPTZ DEFAULT now()
);

-- 成片
CREATE TABLE finished_videos (
    id            BIGSERIAL PRIMARY KEY,
    project_id    BIGINT UNIQUE REFERENCES video_project(id),
    file_path     TEXT NOT NULL,          -- mp4 落盘路径
    duration_sec  NUMERIC(8,2),
    resolution    VARCHAR(16),            -- '1080p' 等
    file_size     BIGINT,
    meta          JSONB,                  -- 各方案附加信息（如 NotebookLM 任务 id、剪映工程名）
    created_at    TIMESTAMPTZ DEFAULT now()
);
```

建表方式沿用现状：`create_tables`（项目无可用 Alembic 环境），在 `models/database.py` 中按现有 Base 风格补模型类。

### 1.3 口播稿分句结构（全链路对齐的"中间表示"）

所有方案共用一个脚本 JSON 结构。**这是音画字幕三方对齐的核心约定**，一旦定稿不要轻易改：

```jsonc
{
  "title": "……",
  "lang": "zh",
  "segments": [
    {
      "idx": 0,
      "text": "最近 AI 圈又出大事了。",
      "pause_after_ms": 300,        // 句后停顿（LLM 生成时给出；TTS 不受它影响，只影响时间轴累计）
      "emphasis": false,            // 可选：重读提示（部分 TTS 支持 SSML 类标记）
      "visual_hint": "AI 大模型发布", // 可选：给画面环节的关键词提示
      // —— 以下字段由配音/合成环节回填 ——
      "audio_path": "work/proj_12/seg_000.wav",   // 逐句音频（方案二/三/四）
      "start_ms": 0,                // 全片时间轴起点（合成前由调度器累计生成）
      "end_ms": 2100
    }
  ]
}
```

要点：

- **方案一**的 segments 来自 ASR 反写（text 与时间戳来自 ASR，无 audio_path——音频是一整条）。
- **方案二**的 segments 来自原视频旁白 ASR；text 用于逐句 TTS。
- **方案三/四**的 segments 来自 LLM 直写（结构化输出，prompt 中明确要求按 JSON schema 返回）。
- **方案五**不使用该结构（剪映内部处理），只在 `video_project.params` 存投喂文本。

### 1.4 新增服务形态与端口规划

对齐现有"独立 FastAPI 服务"模式（3459 登录服务、8000 热点服务）：

| 服务 | 建议端口 | 出现于方案 | 职责 |
|---|---|---|---|
| `notebooklm-service` | 3460 | 一、二 | Playwright 硬控 notebooklm.google.com，仿 3459 四函数形态（check/open/wait/keepalive），接口风格对齐 `/api/quant/*`，如 `/api/nb/create_overview`、`/api/nb/task_status/{id}`、`/api/nb/download/{id}` |
| `tts-service` | 8100 | 二、三、四 | 包 CosyVoice2 推理：`/tts/voices`、`/tts/clone`、`/tts/synthesize`（见 4.4） |
| `video-studio-service` | 8200 | 全部 | 制作主调度服务：任务队列、文案生成、合成管线、音色管理、成片入库〔历史:未建〕 |
| `jianying-automation` | 3461 | 五 | 桌面/UI 自动化驱动剪映客户端或网页版 |

说明：

- 方案一/二共用 `notebooklm-service`；Google 登录态复用 3459 的 `launch_persistent_context` 持久化浏览器模式，`user_data_dir=browser_data/google`（与抖音目录隔离）。
- 方案四的 MoneyPrinterTurbo 自带 FastAPI 服务（默认 8080 端口），可直接部署其原服务，由 `video-studio-service` 反向调用，无需重写其 API。
- `video-studio-service` 在五方案中都是必建项（至少承担任务调度与 ffmpeg 合成），因此**无论选哪个方案，该服务都可先行开发**。

### 1.5 ffmpeg 合成约定（共用合成器）

`video-studio-service` 内建统一合成模块 `synthesizer.py`，约定：

- **工作目录**：`media/projects/{project_id}/`，内含 `seg_*.wav`、`assets/`（画面素材）、`work/`（中间产物）、`output.mp4`。
- **中间格式**：音频一律 48kHz / 16bit / mono 的 wav（TTS 输出统一由 ffmpeg 重采样一次，避免拼接爆音）；画面静帧序列统一 1920×1080 / 30fps 的 png + json 时间轴。
- **字幕**：统一先产出 `.srt`，最终 `burn-in`（`subtitles=...:force_style='FontName=思源黑体,FontSize=16,Outline=1'`），交付物同时保留 mp4 与 srt 文件，便于后续平台上传时用平台自带字幕。
- **标准合成命令骨架**（逐句音频 + 静帧序列）：
  1. 拼接音频：`ffmpeg -f concat -safe 0 -i seg_list.txt -c:a pcm_s16le full_audio.wav`（seg_list.txt 中每句间按 `pause_after_ms` 插入对应时长静音文件，静音文件预生成一份 `sil_{ms}.wav` 缓存复用）。
  2. 画面序列：每 segment 对应一张静帧，动效（Ken Burns）用 `zoompan` 滤镜，转场用 `xfade`；简单首版可直接 `-f concat` 拼静帧视频。
  3. 合成：`ffmpeg -i visuals.mp4 -i full_audio.wav -vf subtitles=proj.srt -c:v libx264 -crf 18 -preset medium -c:a aac -b:a 192k output.mp4`。
- **字幕时间轴来源**：方案三/四直接用逐句累计时间；方案一/二用 ASR 句级时间戳；方案五由剪映内嵌。

### 1.6 登录态与自动化服务规范（方案一/二/五共用）

复用 douyin-login-service 已验证的模式，抽象出平台化约定：

1. **持久化浏览器**：`chromium.launch_persistent_context(user_data_dir=browser_data/{platform}, headless=False)`，单例 + asyncio.Lock，`--disable-blink-features=AutomationControlled` + 隐藏 `navigator.webdriver` init_script——与 3459 完全一致，仅换 user_data_dir 与站点 URL。
2. **四函数骨架**：`check_login()`（以平台特征 Cookie 判定，Google 为 `SID`/`HSID`/`SSID`；剪映为登录态接口探测）、`open_login_page()`、`wait_for_login()`（轮询超时 300s）、`keepalive_touch()`（定时访问首页）。
3. **LangGraph 状态图**：照抄 3459 的 `check_login → open_login_page → wait_for_scan → keepalive → finish` 图结构，改判定条件即可。
4. **小号策略**：NotebookLM 用独立 Google 小号（与主账号隔离，防风控连带）；剪映用独立手机号注册。账号凭据不入库，浏览器指纹落盘即凭据。
5. **风控降级**：连续 2 次自动化操作被拒（验证码/封禁提示）→ 任务标记 `failed` 并告警，冷却 24h，不重试爆号。

## 2. 方案一：纯 NotebookLM 播客——详细设计

> 一句话：NotebookLM 出双人播客音频，ASR 反推时间轴，自研画面按时间轴配图卡，ffmpeg 三合一。**主定位：最快验证"热点→成片"链路，或作为其他方案的文案/旁白素材来源。因音色不可克隆，不能作为满足全部硬性需求的主方案。**
>
> ❌ **【2026-09-26 废弃】** demo 实测否决：音色固定不可克隆，配音与画面内容无法对应（文不对题），一票否决。本章仅作回溯。

### 2.1 全链路逐环节拆解

```
[环节0] 选题          topics 表取最新未制作选题（video_project 落一条 scheme='nb_pure' 记录）
[环节1] 源材料准备     topic.summary + creator_videos.transcript 拼接为 NotebookLM 源文本
[环节2] NotebookLM     Playwright：建 Notebook → 加源 → 触发 Audio Overview → 轮询 → 下载 mp3
[环节3] ASR 反写       mp3 → 现有 transcribe_service（SiliconFlow SenseVoice）→ 句级时间戳
[环节4] 字幕校对       ASR 文本 → LLM 一遍标点/错字校对（保持句数与时长边界不变，只改字词）
[环节5] 画面生成       按 segments 分段 → 每段图卡（LLM 关键词 + 模板渲染 + 可选 AI 生图）
[环节6] 合成           1.5 节合成器：图卡视频轨 + 原始 mp3 + srt 烧录 → output.mp4
[环节7] 入库           finished_videos 落记录，video_project.status='done'
```

### 2.2 各环节实现细节

**环节1（源材料准备）**

- 每次制作新建一个 Notebook（不复用旧 Notebook，避免上下文污染），Notebook 名称用 `topic_{id}_{date}` 便于事后排查。
- 源文本控制在 NotebookLM 上限内（单源约 50 万词，实际拼接热点转写 + 选题摘要足够）；纯文本粘贴方式比上传文件更稳定（省掉文件上传控件自动化）。

**环节2（NotebookLM 自动化）——本方案最大风险点**

`notebooklm-service`（3460 端口）接口设计：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/nb/create_overview` | body: `{source_text, type: "audio"}` → 返回 `{task_id}`，非阻塞 |
| GET | `/api/nb/task_status/{task_id}` | 返回 `{state: generating|done|failed, progress_hint}` |
| GET | `/api/nb/download/{task_id}` | 返回文件流（mp3） |
| GET | `/api/nb/login_status` / POST `/api/nb/open-login-tab` | 登录态四函数，对齐 3459 形态 |

内部流程与选择器策略：

1. 持久化上下文打开 `notebooklm.google.com`，检测 Google 登录态（Cookie SID 存在且访问首页不跳转 accounts.google.com）。
2. 新建 Notebook：定位"新建"按钮（建议用 `get_by_role` + 中文/英文双 selector 兜底：`text=New notebook | text=新建笔记本`）。
3. 粘贴源文本：点击"添加来源"→选"粘贴文本"→填 title 与正文（`page.fill` 逐字段，注意 NotebookLM 的粘贴框是富文本组件，需 `page.evaluate` 直接 set value + dispatch input 事件兜底）。
4. 触发 Audio Overview：点"深度探索/音频概览"→"生成"。**录制 selector 时务必截图留档**，页面改版时只改 selector 表。
5. 轮询：Audio Overview 生成约 1~5 分钟，`task_status` 内部每 15s 查一次 DOM 状态（播放按钮出现/进度条消失），最长等 10 分钟。
6. 下载：Audio Overview 播放器有下载按钮（导出为 mp3）；点击后 Playwright 监听 `download` 事件落盘到 `media/projects/{id}/nb_audio.mp3`。

失败模式与对策：

| 失败 | 对策 |
|---|---|
| Google 风控/验证码 | 状态置 failed，冷却 24h（1.6 节降级约定），人工介入扫码 |
| 每日额度用尽 | NotebookLM 免费版每日生成次数有限，`task_status` 检测到额度提示时返回专用错误码 `QUOTA_EXCEEDED`，调度器当日不再投递任务 |
| 页面改版 selector 失效 | selector 集中在 `selectors.py` 单文件维护；每次失败自动截图存 `logs/nb_fail_{ts}.png` |

**环节3/4（ASR 反写与校对）**

- 直接复用 `transcribe_service.py`：ffmpeg 先转 16k mono wav（播客 mp3 码率足够，无需降级链），调 OpenAI 兼容 `/v1/audio/transcriptions`，请求 `timestamp_granularities` 或带时间戳的响应格式。**注意实测 SenseVoice 免费档是否返回句级时间戳**——若只返回全文，改用 `verbose_json` 格式（segment 级），再实测；这是方案一的第一个 POC 验证点（见 7.2）。
- 双人播客的 ASR 转写无说话人分离也不影响成片（字幕不需要区分说话人）；若后续想按说话人切画面视角，需加 diarization（免费档没有，属增强项，首版不做）。
- LLM 校对 prompt 约束：输入"句列表 + 每句时间戳"，要求"只修正错别字与标点，不得合并/拆分/增删句子，按原句数返回 JSON 数组"。校对后句数与 ASR 不一致则放弃校对结果用原文（宁可字幕有错字不可时间轴错位）。

**环节5（画面生成）**

- 分段策略：按 ASR 句子分组，**每 2~4 句合成一个画面段落**（单句 3~5 秒切一图太跳，画面段落以 10~20 秒为宜）。
- 每段落取该组文本 → LLM 产出 `{keywords, title, bullets[]}` → 图卡模板（首版：Python PIL 绘制——背景底色 + 标题 + 要点列表 + 角标，1080×1920 竖屏或 1920×1080 横屏二选一，先定竖屏适配抖音）。模板引擎单独一个 `card_renderer.py`，与方案三共用。

- 说话人增强（可选）：若 ASR segment 带说话人标记，轮换两种图卡配色模拟"双人视角"；无标记则不做。

**环节6（合成）**：标准合成器（1.5 节）。注意播客 mp3 时长即成片时长，图卡总时长必须覆盖到最后一帧（最后一段图卡按剩余时长延长）。

## 3. 方案二：NotebookLM 画面 + 自研配音——详细设计

> 一句话：白嫖 NotebookLM Video Overview 的高质量画面视频，把原声替换为自研克隆配音，逐句对齐后烧字幕。**核心难点只有一个：音画对齐。**
>
> ✅ **【2026-09-26 保留 + 核心修正】** 换声**必须复述原视频旁白内容**（ASR 原声得到原文案 → 克隆音色逐句重说同样的内容 → 对齐原声时间槽）。禁止把不相干的配音配到画面上——demo2 已按此验证跑通（真实 NotebookLM 视频，12 句逐句换声，11 句自然贴合 1 句槽内加速 1.10x）。GPU 需求：无（TTS 走 API 时）。

### 3.1 全链路逐环节拆解

```
[环节0] 选题            同方案一环节0（scheme='nb_video'）

[环节2] NotebookLM       Video Overview 生成（同 3460 服务，type="video"），下载 mp4
[环节3] 原声解析         mp4 → ffmpeg 抽音轨 → ASR → 原旁白句级时间戳 + 文本
[环节4] 逐句 TTS         按原句文本逐句 CosyVoice 克隆合成 → seg_*.wav
[环节5] 逐句对齐         时长比对 → atempo 变速 / 画面定格延长的决策（核心，见 3.2）
[环节6] 合成             分段视频切割 → 音轨替换 → 拼回 → srt 烧录
[环节7] 入库             同前
```

### 3.2 核心算法：逐句音画对齐

原视频每段画面的时长绑定了原旁白节奏，换配音后逐句处理。设原句 i 的区间为 `[S_i, E_i]`（来自环节3 ASR），原句时长 `D_orig = E_i - S_i`，新配音时长 `D_tts`（实测 wav）：

```
if D_tts <= D_orig:
    # 配音更短：句尾静音补齐到 D_orig（画面自然，无需处理视频）
    pad = D_orig - D_tts
    seg_audio_i = tts_i + silence(pad)
elif D_tts <= D_orig * 1.15:
    # 配音略长：atempo 微加速（1.0~1.15x 内听感无失真）
    speed = D_tts / D_orig
    seg_audio_i = atempo(tts_i, speed)
else:
    # 配音显著更长：不加速（会明显失真），改为把该段画面定格延长
    seg_audio_i = tts_i  # 原速
    mark_segment_stretch(i, target=D_tts)  # 合成环节对该段画面做定格/慢放
```

对齐决策的工程细节：

1. **时长测量**：TTS 输出后用 `ffprobe -show_entries format=duration` 精确测量，勿用 wav 头估算。
2. **句间空隙归属**：ASR 时间戳的句间空隙（通常 0.2~0.8s）保留给原节奏——即新配音段落以 `S_i` 为起点排布，空隙自然留在句尾，与上面"补齐"逻辑一致。
3. **`atempo` 边界**：ffmpeg `atempo` 单级支持 0.5~100，但人耳无感区间约 0.9~1.15；超过 1.15 一律走画面延长，不用 2 级 atempo 串联。
4. **画面定格延长实现**：对第 i 段视频 `[S_i, E_i]` 用 `tpad=stop_mode=clone:stop_duration={extra}` 尾帧定格，或直接把该段放入合成时按新时长重新拼接（因 Video Overview 画面是"图卡+插图+转场"，尾帧定格几乎无违和感；若该段末尾是转场动画则定格会露馅，POC 时抽查）。
5. **整体一致性校验**：所有句处理完后，累计总时长 `T_new` 与原视频 `T_orig` 差值应 < 2s（画面延长会自然吃掉差异）；超出则最后一句强制对齐到片尾。
6. **简化变体（首版强烈建议先做）**：不做逐句处理，TTS 整篇朗读 → 测总长 → 视频整体 `setpts` 变速至等长（0.85x~1.25x 范围内可接受，超出则截取/循环素材）。实现量少约 80%，先验证"换声出片"全链路，再回头做逐句对齐。

### 3.3 环节细节与差异点

**环节1（源材料措辞）**：Video Overview 会自行决定旁白形态（单口/双人）。在源材料末尾显式加一句引导（如"请以单一旁白叙述者的形式制作视频概览"），并 POC 验证中文 Video Overview 的实际形态与质量——**这是方案二可行性的前提**，若中文输出质量差或强制双人，方案二降级。

**环节3（原声解析）**：`ffmpeg -i nb_video.mp4 -vn -ar 16000 -ac 1 audio_orig.wav` → 现有 ASR 链路 → segments（text + start + end）。Video Overview 的旁白是干净人声（无 BGM 或 BGM 很轻），ASR 效果好；若带 BGM 影响转写，先 `highpass/lowpass` 简单滤波。

**环节4（逐句 TTS）**：调用 tts-service `/tts/synthesize`（见 4.4，方案二复用方案三的 TTS 服务）。逐句而非整篇的原因：整篇朗读无法做句级对齐。逐句合成的额外开销是请求次数（一条 3 分钟视频约 40~60 句），本地推理单句约 1~3s，可接受。

**环节6（合成）**：

```
# 1) 按段切视频（重编码切割，保证帧精确）
ffmpeg -ss {S_i} -to {E_i} -i nb_video.mp4 [-vf tpad...] seg_v_{i}.mp4
# 2) 每段合并新音频
ffmpeg -i seg_v_{i}.mp4 -i seg_a_{i}.wav -c:v copy -map 0:v -map 1:a -shortest seg_{i}.mp4
# 3) concat 拼回（同参重编码）
ffmpeg -f concat -i list.txt -c:v libx264 -crf 18 -c:a aac merged.mp4
# 4) srt 来自原句时间戳（对齐后如某段被延长，则其后所有段的时间戳要顺延修正！）
ffmpeg -i merged.mp4 -vf subtitles=proj.srt output.mp4
```

**关键易错点**：凡是走"画面延长"的段落，其后所有段的起始时间都要平移 `extra` 秒——srt 生成必须在段处理完成后基于**最终时间轴**重建，而不是直接抄 ASR 时间戳。实现上建议：先产出"段级新时间轴表"，再从表生成 srt 与切割命令，单一数据源。

## 4. 方案三：文案 + CosyVoice2 全自研链路——详细设计

> 一句话：LLM 写口播稿 → CosyVoice2 本地克隆配音 → 自研画面引擎 → ffmpeg 合成。**五方案中架构最干净、与现有 FastAPI 服务链最契合、完全可控；代价是画面引擎自建的工作量与一张显卡。**
>
> ✅ **【2026-09-26 保留 + GPU 定位修正】**
> - **本地 CosyVoice2（首选）**：**需 NVIDIA 显卡约 4GB 显存**——克隆音色自然度更好、语速/情感可控、音色资产不出本地、零调用成本。用户将提供远程 GPU 机器（SSH 可达），作为正式版首选部署形态。
> - **SiliconFlow API（兜底）**：无需显卡，demo3 已全流程验证；仅在 GPU 机器不可用时兜底，tts-service 内换 provider 即可，接口不变。
> - **原则：GPU 不是负担，是效果上限——只要 GPU 换来更好的效果就用 GPU。**
> - 画面首版为图卡模板；数字人（方案六）作为后续可选升级。

### 4.1 全链路逐环节拆解

```
[环节0] 选题        topics 取数（scheme='cosy'）
[环节1] 文案        LLMClient 扩展 write_script(topic) → 结构化 segments JSON（1.3 节结构）
[环节2] TTS         逐句调 tts-service（CosyVoice2 本地）→ seg_*.wav + 实测时长回填
[环节3] 时间轴      按 seg 时长 + pause_after_ms 累计 → 全片时间轴（天然句级字幕）
[环节4] 画面        visual_hint → 图卡渲染（复用方案一 card_renderer）/ AI 生图 / 素材
[环节5] 合成        标准合成器：画面序列 + 逐句 wav 拼接 + srt → output.mp4
[环节6] 入库        同前
```

### 4.2 环节1：文案生成（write_script）

在 `llm/base_provider.py` 的 LLMClient 上新增方法（不新建服务）：

- **Prompt 要点**（system 部分）：角色定位（如"短视频口播文案作者"）；输出 JSON schema 严格等于 1.3 节 segments 结构；硬约束——单句 ≤ 25 字（TTS 单句过长易出破音且字幕一屏放不下）、总句数按目标时长估算（口播约 4.5 字/秒，60s 视频约 15~20 句）、每句给 `visual_hint`（具体名词性关键词，供画面环节）、开头 3 秒必须有钩子句、结尾给行动号召。
- **响应解析**：复用 DeepSeek 的 JSON mode（`response_format={"type":"json_object"}`）；解析失败重试一次（prompt 中追加错误说明），再失败任务置 failed。
- **可选进阶**：`style` 参数（播客对话体/单人口播体/新闻播报体）作为 prompt 模板变量，`video_project.params.style` 落库。
- NotebookLM 播客反写（Audio Overview → ASR → 对话式文案）作为备选文案源，接口上同样产出 segments 结构——但 pause/emphasis 等字段需从 ASR 时间戳反推。首版不做，留作风格实验。

### 4.3 环节2/3：TTS 与时间轴

**CosyVoice2 本地部署规格**：

- 仓库：FunAudioLLM/CosyVoice2-0.5B；推理显存约 4GB 起（batch=1、短句），建议 6~8GB 余量；Windows 下建议直接用 WSL2 或 Docker 跑（官方以 Linux 为准），GPU 需 NVIDIA + CUDA。
- 部署形态：tts-service（8100 端口）内嵌模型，加载一次常驻显存；**不要每请求冷启动**（模型加载 30s+）。
- 克隆模式：`{text, prompt_text, prompt_speech_16k}` zero-shot 推理——每次合成携带 3~10s 样本音频；样本预处理好后缓存于内存（voice_id → 样本张量），避免每次重做特征提取。
- 音色注册流程（`/tts/clone`）：上传录音 → 质量自检（静音段检测、削波检测、有效时长 3~10s、信噪比粗估，librosa 实现）→ 落盘 `media/voices/{voice_id}.wav` → tts_voice 表入库。自检不过返回明确错误（用户重录）。

**tts-service 接口定义**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/tts/voices` | 音色列表 |
| POST | `/tts/clone` | multipart 上传录音 → 质量自检 → 注册 voice_id |
| POST | `/tts/synthesize` | body: `{voice_id, text, speed=1.0}` → 返回 wav 文件流 + 响应头 `X-Audio-Duration` |
| DELETE | `/tts/voices/{voice_id}` | 删除音色 |

**时间轴生成**：逐句合成完毕后统一累计（伪代码）：

```
t = 0
for seg in segments:
    seg.start_ms = t
    seg.end_ms = t + measured_dur_ms(seg)
    t = seg.end_ms + seg.pause_after_ms
total = t
```

字幕与画面分段共用该时间轴，**无需 ASR**。可选校准（增强项）：对拼接后的 full_audio 跑一遍 ASR，与预期时间轴比对，偏差 > 300ms 的句报警——用于发现 TTS 吞句/异常静音。

### 4.4 环节4：画面引擎（本方案主要工作量）

分层实现，首版只做第 1 层：

1. **图卡模板层（首版）**：复用方案一的 `card_renderer.py`。文案 segments 的 `visual_hint` → LLM 归并为画面段落组（每 2~4 句一组，同方案一策略）→ 每组一张图卡。投入点：设计 3~5 套模板（新闻风/科技风/科普风），色板与字体固化配置。
2. **AI 生图层（二期）**：`visual_hint` → SiliconFlow SDXL txt2img（复用 docker/.env 中现有 SiliconFlow 鉴权）→ 1080p 图作图卡背景或全幅背景+半透明蒙层+字幕。生图成本约几分钱/张，每片 8~15 张。
3. **素材库层（可选）**：关键词 → Pexels/Pixabay API 拉视频片段 → 按段落时长裁切。国内访问速度需实测（方案四的已知问题，此处同）。
4. **数字人层（远期可选）**：HeyGem 本地部署，口播音频 + 一段真人底板视频 → 口型同步。属独立子系统，不阻塞主线。

动效：首版 Ken Burns（`zoompan` 慢推）+ 0.3s `xfade` 转场即可显著提升质感，参数固化在模板配置里。

## 5. 方案四：开源全家桶 MoneyPrinterTurbo 改造——详细设计

> 一句话：MoneyPrinterTurbo（MIT，FastAPI 架构）已实现"文案→TTS→配画面→字幕→成片"全链路，部署它作为渲染引擎，自有服务只做选题、文案、音色克隆的接入与调度。**工作量最小的全可控方案。**
>
> ❌ **【2026-09-26 废弃】** demo4 实测否决：关键词匹配的素材画面与内容相关度差、观感不可用。画面文对题改走方案六（LLM 分镜 + AI 生图）。本章仅作回溯。

### 5.1 部署与架构决策

**部署形态二选一**（7.1 待定项之一）：

- **A. 整项目部署**：直接 `docker compose up` 其官方容器（自带 MoviePy/ffmpeg/Redis 依赖），自有 `video-studio-service` 通过其 HTTP API 驱动。优点：升级简单；缺点：多一套 Redis/任务队列，接口字段与自己数据模型有翻译层。
- **B. 只抽取渲染模块**：把其 `services/` 中素材匹配、视频合成、字幕生成模块作为库引入（MIT 无协议障碍）。优点：架构统一、无翻译层；缺点：吃透其内部耦合的改造工作量反而可能超过部署，且放弃上游升级。

**建议：先 A 后 B**——A 验证产出质量达标后，若翻译层摩擦确实大再评估 B。理由：该项目的核心价值在其素材匹配与合成管线的调优经验，抽取模块容易"抽断了依赖蛛网"。

### 5.2 集成改造点清单

MPT（MoneyPrinterTurbo）原链路：`task_id → 文案 → TTS(其内置 edge-tts 等) → 素材下载(Pexels/Pixabay) → MoviePy 合成 → 字幕(whisper 对齐)`。改造如下：

| # | 改造点 | 方式 | 工作量 |
|---|---|---|---|
| 1 | 文案不改 MPT | 自有 LLMClient 写稿后，调 MPT API 时直接传 `video_subject` + `video_script` 参数（其 API 支持外部传稿） | 0 |
| 2 | **TTS 替换为克隆音色**：MPT 内置 TTS 不可克隆 | 两条路：(a) 配置 MPT 使用其支持的 Azure/其他可克隆 TTS——不支持 CosyVoice；(b) **推荐**：自有侧先用 tts-service 逐句合成好音频，把 MPT 的 TTS 环节跳过（其 API/任务参数中传已备好的音频路径，或 fork 一层适配） | 中（1~2d，取决于其参数开放度，需读其 task 模型源码确认） |
| 3 | 字幕：MPT 内置 whisper 对齐可用 | 直接沿用；或传自有逐句时间轴关闭其字幕环节、由自有合成器烧字幕 | 小 |
| 4 | 素材源国内化 | Pexels/Pixabay 国内访问慢的实测替换为国内可直连源；MPT 素材 provider 有配置项 | 小（实测驱动） |
| 5 | 画面模板感弱化（可选） | 注入自有图卡/AI 生图作为"素材"（MPT 支持本地素材目录） | 小 |
| 6 | 任务回调 | MPT 任务完成无 webhook 的话，轮询其任务状态接口 → 回写 video_project | 小 |

### 5.3 全链路（改造后）

```
topics → LLMClient.write_script
       → tts-service 逐句合成（克隆音色）→ full_audio.wav + 句级时间轴
       → MPT API（传稿 + 传音频 + 素材配置）→ MPT 配画面/合成/字幕 → mp4
       → 轮询取件 → ffmpeg 后处理（可选片头/封面）→ finished_videos 入库
```

TTS 克隆引擎选型与方案三完全共用（CosyVoice2 本地 / IndexTTS-2 / GPT-SoVITS / SiliconFlow API），tts-service 引擎适配层设计见 4.3/4.6，此处不重复。差异仅在：MPT 路线下"画面+合成+字幕"外包给了 MPT，自有合成器只做兜底。

### 5.4 开发任务拆解

| 任务 | 产出 | 估时 |
|---|---|---|
| MPT docker 部署 + API 跑通（官方示例任务） | 渲染引擎可用 | 1d |
| write_script（同方案三任务） | segments 产出 | 1d |
| TTS 前置合成 + MPT 传音频适配（改造点 2） | 替换其 TTS | 2d |
| tts-service（同方案三，若未先行） | 依赖项 | 3d（计入方案三） |
| 素材源实测与替换 + 任务轮询 + 入库 | 端到端 | 2d |
| 联调出片 + 质量评估 | POC 报告 | 1d |
| **合计（不含 tts-service）** | | **约 7d**（五方案中除方案五外最小） |

### 5.5 验收标准与风险

验收：真实选题端到端出片；素材与文案相关度抽查（10 片中 ≥ 7 片画面主题正确）；克隆音色正常；字幕无错位。

| 风险 | 等级 | 对策 |
|---|---|---|
| MPT 内部对"外部传入音频"支持不佳，改造点 2 工作量膨胀 | 中 | POC 首日读其 task 模型源码确认参数开放度；不行则评估 B 形态或退方案三 |
| 素材库访问慢/相关度差 | 中 | 国内源替换 + 注入自有生图素材（改造点 5） |
| MPT 上游升级与自有改动的合并成本 | 低 | 改动收敛在 fork 的适配层文件，不散落 |
| 云端克隆 API 的录音隐私 | 低 | 本地部署优先；走 API 时用户协议告知 |

## 6. 方案五：剪映图文成片自动化——详细设计

> 一句话：DeepSeek 写稿 → UI 自动化驱动剪映"图文成片"（自动配画面/配音/字幕）→ 导出成片。**投入最小、观感上限取决于剪映模板生态；但音色资产封闭、自动化脆弱，只适合半自动人机协作。**
>
> ❌ **【2026-09-26 废弃】** 需要人工参与，无法无人值守，与自动化出片目标冲突。本章仅作回溯。

### 6.1 技术路线选择（先定这个）

| 路线 | 说明 | 评估 |
|---|---|---|
| 剪映专业版（Windows 桌面客户端）"图文成片" | pywinauto/uiautomation 桌面 UI 自动化 | 客户端功能全（含声音复刻）；但控件树复杂、弹窗多、自动化最脆弱 |
| 剪映网页版 | Playwright 驱动 | 复用现有 Playwright 技术栈与 1.6 节服务形态；**功能子集，需 POC 确认网页版是否有图文成片与声音复刻** |
| 剪映小助手/云剪辑 | 部分能力在云端，可能有接口 | 抓包分析成本高，且非官方接口有风控风险 |

**建议：网页版 Playwright 优先 POC，功能缺失再回桌面客户端。** 若走桌面客户端，自动化服务形态从"Playwright 服务"改为"驻留 Windows 会话的桌面自动化 worker"（需要保持桌面会话解锁，服务器场景需配置自动登录，部署约束要在选型时明说）。

### 6.2 全链路拆解（以网页版为例）

```
[环节0] 选题（scheme='jianying'）
[环节1] 文案    LLMClient.write_script（复用方案三，输出纯文本串接版投喂）
[环节2] 自动化  Playwright：登录态检查 → 进入图文成片 → 粘贴文案 → 选音色（声音复刻列表）→ 生成
[环节3] 等待    剪映服务端生成（分钟级），轮询生成状态
[环节4] 导出    触发导出 → 等待 → 下载 mp4（或云素材下载链接）
[环节5] 后处理  可选：ffmpeg 加片头/片尾/水印/封面（剪映导出物直接可用则跳过）
[环节6] 入库    finished_videos（meta 记录剪映工程名/音色名）
```

自动化细节：

- **登录态**：1.6 节四函数（剪映判定改为调其用户信息接口或页面头像元素）；剪映登录多为手机验证码，**无法全自动**，扫码/验证码环节必须人工参与一次，之后依赖持久化会话续命 + 定时保活。
- **声音复刻**：需在剪映内人工录制约 10 句完成注册（一次性人工操作，自动化价值低）；注册后的复刻音色出现在音色列表，自动化只需"选中它"。无法通过 API 批量注册/导出音色——这就是"音色资产封闭"的具体含义。
- **批量与队列**：生成与导出均为分钟级同步等待，`jianying-automation` 服务内部维护单浏览器串行队列（并发多开会触发风控），外部看就是 `/api/jy/submit`（入队）+ `/api/jy/task_status/{id}`（轮询）两个接口。
- **频率与会员**：部分音色/素材是会员权益（收费）；免费档每日生成次数有限。队列里做当日配额计数。

### 6.3 开发任务拆解

| 任务 | 产出 | 估时 |
|---|---|---|
| 网页版功能 POC（图文成片/声音复刻是否存在且可自动化） | POC 结论（决定走网页还是桌面） | 1d |
| 自动化服务骨架 + 登录态四函数 | 3461 服务 | 2d |
| 图文成片全流程自动化（粘贴/选音色/生成/导出） | `/api/jy/*` | 3d |
| 串行队列 + 配额 + 后处理 + 入库 | 端到端 | 2d |
| 联调与稳定性压测（连续 10 任务成功率） | POC 报告 | 1d |
| **合计** | | **约 9d**；若回桌面客户端 +2~3d 且部署约束增加 |

### 6.4 验收标准与风险

验收：半自动流程（人工登录一次后）连续 10 个任务成功率 ≥ 70%；成片字幕/配音/画面完整；每日配额内稳定产出。

| 风险 | 等级 | 对策 |
|---|---|---|
| 音色复刻封闭，无法自建音色资产库 | **高（硬性需求只算大致满足）** | 选型时明确接受度；不接受则排除本方案 |

| 会员收费/每日配额 | 低 | 配额计数 + 关键功能用免费档验证 |
